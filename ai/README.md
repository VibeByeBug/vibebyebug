# Ready-Q — AI 모듈

담당: 이예진 · 팀 레포 `VibeByeBug/vibebyebug`

## 백엔드와의 계약 (STT 무관)

AI 모듈은 STT 구현을 모릅니다. 아래 두 메시지만 들어오면 동작합니다.

```
C→S  {type:"stt.partial", text, ts}    # 말하는 중 (투기적 검색 시작)
C→S  {type:"stt.final",   text, ts}    # 발화 종료
S→C  {type:"cue.evidence", keywords[], sources:[{slide, snippet}], latency_ms, mode}
S→C  {type:"cue.answer",   text, done, latency_ms, status}   # answer 모드에서만, 문장마다 갱신
S→C  {type:"cue.summary",  summary, question_type, delta:true}
```

STT 선정 필수 조건: **interim(부분) 결과 스트리밍 지원.** 없으면 투기적 파이프라인이
불가능해 1초 예산이 깨집니다. 그리고 "발화 끝 → final 도착" 지연을 측정해서 알려주세요 —
그 값이 AI 쪽 예산의 입력값입니다.

## 인덱싱 파이프라인 (두 경로)

발표자료는 두 종류입니다. 둘 다 `chunks.jsonl` 이라는 같은 형식으로 끝나므로,
그 뒤(임베딩·검색)는 어느 경로로 왔는지 구분할 필요가 없습니다.

```
글자가 살아있는 자료 ─ ingest.py ─────────────┐
                                              ├─→ chunks.jsonl → 임베딩 → 검색
글자가 이미지인 자료 ─ render.py → caption.py ─┘
```

`ingest.py` 는 텍스트를 못 찾으면 **조용히 0건을 쓰지 않고 종료코드 3으로 실패**합니다.
검색이 못 보는 구간을 발표자가 모르는 것이 이 제품에서 가장 위험한 실패 양상이라,
파이프라인 전체가 "못 읽었으면 반드시 말한다"를 지킵니다.

### 자동 전환 (`build_chunks.py`)

서버는 올라온 자료가 어느 쪽인지 미리 모른다. `build_chunks.build()` 가 둘을 알아서 고른다.

1. 글자 추출을 먼저 한다. 글자가 다 있으면 여기서 끝나고 API 호출은 0회다.
2. 글자가 20자 미만인 슬라이드만 이미지로 만들어 읽는다. 섞인 자료는 모자란 장만 읽는다.
3. 키가 없거나 하루 한도가 떨어져도 멈추지 않는다. 글자로 뽑은 장은 살리고,
   못 읽은 장 번호(`unreadable`)와 이유(`reason`)를 돌려준다.

```python
from build_chunks import build
r = build(path, slides_dir=f"data/slides/{presentation_id}")
r["rows"]        # ingest() 와 같은 형식. 그대로 jsonl 로 쓰면 된다
r["method"]      # text | image | mixed
r["unreadable"]  # 끝내 못 읽은 슬라이드 번호
r["reason"]      # no_api_key | daily_quota | call_limit | render_failed | caption_error | None
r["message"]     # 화면에 띄울 문구
r["calls"]       # 이번에 쓴 API 호출 수
```

`slides_dir` 를 발표마다 고정하면 같은 자료를 다시 올려도 이미 읽은 장은 호출하지 않는다.
하루 한도 때문에 일부만 읽혔다면 다음 날 다시 올리면 나머지만 읽는다.

주의할 점 두 가지.

- 슬라이드 한 장에 호출 1회다. Gemini 무료 등급은 하루 20회라 18장 자료 하나로 거의 다 쓴다.
  `max_calls` 로 한 번에 쓸 상한을 걸 수 있다.
- PPTX 를 이미지로 만들려면 PowerPoint 가 깔린 윈도우가 필요하다. PDF 는 어디서나 된다.

확인한 경우: 글자만 있는 PDF(호출 0회), 글자 1장 + 이미지 2장 PDF(호출 2회, 재실행 시 0회),
키 없음, 호출 상한 0, 하루 한도 초과. 마지막 셋은 모두 글자 1장을 살리고 2, 3번을 못 읽은 장으로 돌려줬다.

| `drill_graph.py` | 꼬리질문 멀티턴 (LangGraph) | 동작 확인 |

```bash
# 글자가 있는 자료
python ingest.py 발표자료.pptx -o data/chunks.jsonl
python quality_report.py data/chunks.jsonl        # 0=양호 1=경고 2=실패

# 글자가 이미지인 자료
python render.py 발표자료.pptx -o data/slides
python caption.py data/slides --dry-run           # 호출 건수 미리보기 (키 불필요)
python caption.py data/slides -o data/chunks.jsonl --source 발표자료.pptx
```

API 키는 환경변수로 둡니다 (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`).
`caption.py` 가 설정된 키를 보고 제공사를 자동 선택하며, `--provider` 로 덮어쓸 수 있습니다.
캡션은 슬라이드 이미지 + 프롬프트 + 모델명을 해시해 캐시하므로, 다시 돌려도 중복 호출이 없고
프롬프트나 모델을 바꾸면 자동으로 무효화됩니다.

## 설계 결정

**청크 단위 = 슬라이드.** 산출물이 "키워드 + 슬라이드 출처"라서 인용 단위가 곧 검색
단위입니다. 더 잘게 쪼개면 검색은 나아져도 "몇 번 슬라이드"를 못 돌려줍니다.

**캡션은 요약이 아니라 전사.** 모델이 지어낸 문장이 근거로 저장되면 Ready-Q 가 내세우는
'환각 방지'가 인덱싱 단계에서부터 무너집니다. 프롬프트에서 요약·반올림·추측을 금지하고
"안 보이면 빼라"를 명시합니다.

**핫패스에서 LLM 빼기 (검증 대상).** 유형 태그는 분류 문제라 임베딩+분류기로 ~20ms,
1줄 요약은 STT 텍스트 자체로 갈음 가능. 되면 첫 렌더가 STT 지연에만 묶입니다.

## 무료 등급 속도 제한 주의

Gemini 무료 등급은 **모델당 분당 5회**입니다. 워커를 4개로 두면 바로 429 가 나서
18장 중 6장이 통째로 날아갑니다(실제로 겪음). 그래서:

- 기본 워커 수를 2로 낮췄습니다.
- 429 를 만나면 서버가 알려준 `retryDelay` 만큼 기다렸다 재시도합니다(최대 6회).
- 404 처럼 기다려도 소용없는 오류는 즉시 포기합니다.

모델명이 바뀌는 것도 겪었습니다 — `gemini-2.5-flash` 는 신규 사용자에게 막혀 있어
`gemini-3.6-flash` 로 바꿨습니다. 모델 ID 는 하드코딩하지 말고 `--model` 로 넘기세요.

## [정정] 지연 측정이 틀렸었다 (2026-09-05)

아래 bake-off 표의 `질의ms` 는 **틀린 값이다.** 질문 45개를 한 번에 넣고 45로 나눠 쟀는데,
그러면 모델 호출 한 번을 45개가 나눠 써서 실제보다 싸게 나온다.
실제 서비스는 질문이 하나씩 들어온다.

    묶어서 45개 : 질문당 378ms   <- 이렇게 쟀다
    하나씩      : 질문당 595ms   <- 실제

정확도(R@1/R@3/R@5/MRR)는 영향 없다. 지연만 틀렸다.
`eval_retrieval.py` 는 이제 질문 하나씩 재고 p50 과 **p95** 를 같이 낸다.

### 다시 잰 값 (문서 289장, 질문 45개, 질문 하나씩)

| 검색기 | R@3 | p50 | p95 | 색인(warm) |
|---|---|---|---|---|
| hybrid(BM25+BGE-M3) | 93.3% | 584ms | **2,215ms** | 721초 |
| **hybrid(BM25+e5-small)** | **88.9%** | **169ms** | **428ms** | **62초** |
| BGE-M3 단독 | 84.4% | 421ms | 608ms | 515초 |
| BM25 단독 | 80.0% | 0.7ms | 1.2ms | 0초 |
| e5-small 단독 | 75.6% | 93ms | 206ms | 122초 |
| ko-sroberta 단독 | 68.9% | 142ms | 384ms | 88초 |

**BGE-M3 하이브리드는 핫패스에서 못 쓴다.** p95 2.2초는 1초 예산의 두 배다.
스무 번에 한 번은 발표자가 이미 답을 시작한 뒤에 근거가 뜬다. 색인도 12분이다.

**권장: `BM25 + e5-small`.** 정확도 4.4%p 를 내주고 p95 를 5분의 1로 줄인다.
e5-small 은 118M 으로 BGE-M3(568M)의 5분의 1이다. 실시간에 인코딩하는 것은
질문 한 줄뿐이므로 큰 모델이 과하다.

**임베딩 단독으로는 못 쓴다.** e5-small 혼자면 75.6% 로 BM25(80.0%)보다도 낮다.
BM25 와 묶어야 88.9% 가 된다. 단어 매칭과 의미 매칭을 합쳐야 한다는 결론은 그대로다.

### p50 이 아니라 p95 로 예산을 잡을 것

BGE-M3 하이브리드는 p50 584ms / p95 2,215ms 로 3.8배 벌어진다.
평균이 예산 안이어도 스무 번에 한 번 넘으면 발표 중에는 그게 사고다.

### 최종 선택은 STT 측정값에 달렸다

    STT 400ms -> 남는 600ms -> BGE-M3 하이브리드도 검토 가능
    STT 800ms -> 남는 200ms -> e5-small 도 p95 로는 빠듯

백엔드의 "발화 끝 -> final 도착" 측정값이 오면 확정한다. 세 후보를 다 살려둔다.

## 검색기 bake-off 결과 (2026-09-04)

문서 289장(톰과젤리 18 + 랩미팅 10편 271), 손으로 쓴 질문 45개 기준.

| 검색기 | R@1 | R@3 | R@5 | MRR | 질의당 |
|---|---|---|---|---|---|
| **hybrid(BM25+BGE-M3)** | **71.1%** | **93.3%** | **95.6%** | **0.817** | 216.8ms |
| KURE-v1 | 66.7% | 88.9% | 93.3% | 0.769 | 194.1ms |
| BGE-M3 | 66.7% | 84.4% | 88.9% | 0.762 | 312.9ms |
| BM25 | 57.8% | 80.0% | 82.2% | 0.683 | **0.9ms** |

**문서 수를 늘리자 순위가 뒤집혔다.** 톰과젤리 18장만 썼을 때는 KURE-v1 이 R@3 95.6% 로
1위였는데, 방해 문서 271장을 넣자 88.9% 로 떨어졌다. 같은 조건에서 hybrid 만 93.3% 그대로였다.

| 검색기 | R@3 (18장) | R@3 (289장) | 변화 |
|---|---|---|---|
| hybrid | 93.3% | 93.3% | 0 |
| KURE-v1 | 95.6% | 88.9% | -6.7 |
| BGE-M3 | 91.1% | 84.4% | -6.7 |
| BM25 | 88.9% | 80.0% | -8.9 |

hybrid 는 단어 매칭(BM25)과 의미 매칭(임베딩) 두 신호를 RRF 로 합치므로, 방해 문서가
한쪽을 속여도 다른 쪽이 잡는다. 단일 검색기는 그 하나가 속으면 방법이 없다.

**결론: hybrid 를 쓰되 2단계로 띄운다.**

```
질문 들어옴 -> BM25 결과 즉시 표시  (0.9ms,  R@3 80%)
            -> hybrid 로 갱신       (217ms,  R@3 93%)
```

BM25 혼자서도 열 중 여덟은 맞고 1ms 면 체감 지연이 없다.

**다만 2단계에서 순서가 거의 매번 바뀐다.** 실측 8개 중 7개에서 상위 3개가 달라졌다.
'1단계가 대체로 맞고 2단계가 가끔 고쳐준다'는 전제는 성립하지 않는다.
발표자가 이 흔들림을 견딜 수 있는지는 숫자로 답할 수 없고 화면에 띄워봐야 안다.

**주의: 표본이 작다.** 질문 45개라 hybrid 와 KURE-v1 의 차이(93.3 vs 88.9)는 질문 2개다.
믿을 값은 절대 순위가 아니라 **"방해 문서를 넣었을 때 hybrid 만 안 떨어졌다"는 패턴**이다.
검색기 4개에서 방향이 일관됐다.

**남은 약점: 절차형 질문.** 놓친 3개가 전부 내용이 아니라 '어떻게/왜'를 묻는 질문이었다.
문서 18장일 때도 같은 패턴이라 검색기 교체로 풀릴 문제가 아니다.

## 질문셋을 손으로 쓴 이유

`make_questions.py` 로 모델에게 시켰더니 무료 등급 분당 5회 제한 + 503 혼잡 + DNS 오류로
45분간 한 개도 못 얻었다. 캡션 결과가 이미 로컬에 있어 직접 읽고 쓰는 편이 빠르고,
'슬라이드 문장 베끼지 않기 / 정답 숫자 넣지 않기' 규칙을 확실히 지킬 수 있다.
질문에 숫자가 섞였는지는 자동 점검한다(현재 0건).

정답은 **여러 개를 허용**한다(`gold_ids`). 이 발표는 `6,447곳` 이 6개 슬라이드에 반복 등장해서,
정답을 하나로 고정하면 검색기가 맞는 슬라이드를 찾고도 오답 처리된다.

## 질문 유형 분류 (2026-09-04)

핫패스 산출물이 '요약 1줄 + 유형 태그' 라, 유형 태그를 LLM 없이 뽑을 수 있는지 쟀다.

| 방법 | 정확도 | 비용 |
|---|---|---|
| **키워드 규칙 (`qtype.classify`)** | **93.3%** | **0ms** |
| 최다 클래스만 찍기 | 46.7% | 0ms |
| 임베딩(BGE-M3) + kNN | 42.2% | 모델 2.2GB |

**임베딩이 아무거나 찍는 것보다 못하다.** 한계반론은 6개 중 0개를 맞혔다.
임베딩은 '무슨 얘기인지'를 벡터로 만드는데 유형은 '어떻게 묻는지'로 정해지기 때문이다.
"AI 성능이 얼마나 나왔나요"(사실확인)와 "AI가 틀리면 어떻게 되나요"(한계반론)는
주제가 같아 임베딩상 이웃이지만 유형이 다르다.

**결론: 핫패스에서 LLM 도 임베딩도 뺀다.** 유형 태그는 정규식으로 끝난다.

유형은 '발표자가 어떻게 대응해야 하는가' 로 나눴다. 태그가 떠도 대응이 안 달라지면
쓸모없는 정보다.

| 유형 | 비중 | 발표자가 할 일 |
|---|---|---|
| 사실확인 | 47% | 숫자를 그대로 읽으면 끝 |
| 절차 | 24% | 단계를 순서대로 |
| 근거 | 16% | 검증 슬라이드로 |
| 한계반론 | 13% | 방어·우회 화법 (계획서의 우회 템플릿이 여기서 발동) |

**주의:** 규칙을 45개의 정답을 본 뒤에 썼고, 오답을 보고 한 번 더 고쳤다. 93.3% 는
낙관적이다. 임베딩은 leave-one-out 교차검증을 했고 규칙은 안 했으므로 공정한 비교도
아니다. 다만 "임베딩이 최다 클래스 찍기보다 못하다" 는 규칙과 무관하게 성립한다.

## 절차형 질문 - 시도 두 개 다 실패 (2026-09-04)

hybrid 가 놓친 3개가 전부 '어떻게/왜' 를 묻는 절차형이었다. `diagnose_misses.py` 로
무엇에 밀렸는지 봤더니 원인이 둘이었다.

1. **희석** - 답이 긴 슬라이드의 한 줄에 있는데 슬라이드 전체를 통으로 채점하니,
   처음부터 끝까지 그 주제인 슬라이드가 이긴다.
2. **어휘 격차** - 질문 "순위를 매길 때 뭘 먼저 보고 정하신 건가요" 와
   슬라이드 "선정 규칙 : (1) 사고 유무 -> (2) 보수 횟수" 는 같은 뜻인데 겹치는 글자가 없다.

### 시도 1: 구간 단위 채점 (`MaxPassage`) - 채택 안 함

| 검색기 | R@3 | 질의당 |
|---|---|---|
| hybrid (기존) | 93.3% | 216.8ms |
| hybrid + 구간채점 | 93.3% | **1,302ms** |
| BGE-M3 단독 | 84.4% | 244ms |
| BGE-M3 + 구간채점 | **91.1%** | 604ms |

놓친 질문 3개가 그대로다. 희석은 실재해서 **임베딩 단독은 +6.7%p** 올랐지만,
하이브리드는 BM25 가 이미 그 부분을 보완하고 있어 더 얻을 게 없었다.
그리고 1,302ms 는 1초 예산을 검색 혼자 넘긴다. **임베딩 하나만 쓸 때는 유효한 카드다.**

### 시도 2: 유형별 검색어 확장 (`qtype.EXPANSION`) - 폐기

| 검색기 | R@3 | 변화 |
|---|---|---|
| BM25 | 80.0% -> **68.9%** | -11.1%p |
| hybrid | 93.3% -> **84.4%** | -8.9%p |

확장어("규칙 선정 기준 순서 단계 ...")가 거의 모든 슬라이드에 있는 흔한 말이다.
BM25 는 드문 단어에 높은 점수를 주는데 흔한 단어를 얹으니 질문을 구별해주던 단어가
묻혔다. 표적 3개를 건지려다 나머지 42개를 망가뜨렸다.

### 결론

**기존 hybrid 217ms 를 그대로 쓴다.** 절차형 일부가 4~6위로 밀리는 것은 안고 간다.
다시 볼 곳은 검색이 아니라 제품 쪽이다 - hybrid 의 R@5 가 95.6% 이므로, 화면에 근거를
3개가 아니라 5개 띄우면 검색을 안 건드리고 일부가 회수된다. 프론트와 정할 문제다.

## [결정] 2단계를 버리고 한 번에 띄운다 (2026-09-05)

처음엔 BM25 로 즉시 띄우고(3ms) 정확한 결과로 갱신하는(428ms) 2단계로 설계했다.
"빈 화면이 제일 나쁘다"는 전제였는데, **그 전제를 검증하지 않았다.**

실측해보니 8개 질문 중 **4개에서 1위 카드가 교체**되고 7개에서 순서가 바뀌었다.
그리고 갱신이 428ms 에 도착한다 - **발표자가 화면으로 눈을 옮기는 시간과 비슷하다.**

    질문 종료 -> (발표자가 질문을 소화하고 고개를 돌림) -> 눈이 카드에 닿음
                                                            ^ 이 순간 내용이 바뀐다

1단계를 읽을 틈은 없고 바뀌는 것만 보인다. **값은 못 하고 흔들림만 남는다.**
428ms 빈 화면은 사람이 '느리다'고 느끼는 구간(대략 1초)에 한참 못 미친다.

**그래서 단일 단계로 간다.** API 도 계약도 단순해졌다 - `rq.cue(question)` 하나다.

2단계 비교용 메서드(`_fast_cue` / `_refined_cue`)는 진단용으로 남겨둔다.

## 핫패스 (`pipeline.py`)

백엔드가 붙일 대상이다. STT 구현을 모르고 텍스트만 받는다.

```python
rq = ReadyQ("data/chunks.jsonl")   # 기본 = balanced
rq.warm()                           # 발표 시작 전 1회

cue = rq.cue(question)              # 이거 하나면 된다
cue.to_message()                    # cue.evidence 형태의 dict
```

**중간 결과를 먼저 띄우지 않는다.** 기다렸다 한 번에 준다.

2단계 검색기는 프리셋으로 고른다. 어느 걸 쓸지는 STT 가 예산을 얼마나 쓰느냐로 정해진다.

| 프리셋 | 구성 | R@3 | p50 | p95 | 색인 |
|---|---|---|---|---|---|
| `fast` | BM25 만 (2단계 없음) | 80.0% | 0.7ms | 1.2ms | 0초 |
| **`balanced`** (기본) | BM25 + e5-small | 88.9% | 169ms | 428ms | 62초 |
| `accurate` | BM25 + BGE-M3 | 93.3% | 584ms | 2,215ms | 721초 |

```python
rq = ReadyQ("data/chunks.jsonl", preset="fast")      # 2단계 없음
```
```bash
python pipeline.py data/chunks.jsonl "질문" --preset fast
```

`fast` 는 `warm()` 이 0초에 끝나고, `refined_cue()` 를 부르면 **조용히 넘어가지 않고**
왜 안 되는지 말한다. 조용한 실패 경로를 만들지 않는다.

```bash
python pipeline.py data/chunks_tomjelly.jsonl "이 분석의 한계는 뭐라고 보시나요?"
```

내보내는 메시지 (`Cue.to_message()`):

```json
{
  "type": "cue.evidence",
  "question_type": "한계반론",
  "keywords": ["개별", "예측", "도구", "스크리닝", "우선순위"],
  "sources": [
    {"slide": 17, "snippet": "• 개별 사고를 예측하는 도구가 아니라, ...", "source": "발표.pptx"}
  ],
  "deflect": ["그 부분은 저희도 한계로 보고 있습니다. 자료에 이렇게 적어뒀습니다 —"],
  "stage": "fast",
  "latency_ms": 1.2
}
```

`deflect` 는 한계반론 유형에만 붙는다. 계획서의 우회 화법이 여기서 나온다.
답을 대신 만들지 않고 '말하는 방식'만 제안한다.

### 키워드는 만들지 않고 뽑는다

계획서의 '환각 방지' 가 지켜지는 지점이다. 슬라이드에 실제로 있는 줄을 고르고,
그 줄에서 명사만 꺼낼 뿐이다. 없는 말은 화면에 뜨지 않는다.

**형태소 분석기(kiwipiepy)를 쓴다.** 정규식으로 조사를 자르는 방식은 '많았기',
'찾도록', '둘째' 같은 동사·부사 조각을 못 걸렀다. 화면에 뜨는 키워드라 바로 티가 난다.
숫자는 뒤따르는 단위와 다시 붙인다(`3` + `회` -> `3회`). Q&A 는 수치를 물어보므로
`1.47배`, `33,000장`, `0.96` 같은 형태가 살아 있어야 한다.

**줄별 명사는 색인 때 미리 계산한다.** 질의마다 후보 슬라이드의 모든 줄을 분석하면
74ms 가 붙었다. 미리 해두니 1.2ms 다(60배).

### 유형 태그가 여기서 값을 한다

검색에 유형을 쓰는 건 실패했지만(위 참고), **무엇을 띄울지** 고르는 데는 맞다.

| 유형 | 어떤 줄을 밀어주나 |
|---|---|
| 사실확인 | 숫자가 있는 줄 |
| 절차 | (1)(2)(3), 규칙, 순서, 단계가 있는 줄 |
| 근거 | p=, ρ, 배, %, 검증, 대조가 있는 줄 |
| 한계반론 | 한계, 아니라, 제외, 가상, 근사가 있는 줄 + 우회 화법 |

## 모의 디펜스 (`mock_defense.py`)

계획서의 [사전] 단계다. 발표 전에 예상 질문으로 연습하고 무엇을 놓쳤는지 본다.

```bash
python mock_defense.py gen   data/chunks.jsonl -o data/expected.jsonl --per-type 5
python mock_defense.py drill data/chunks.jsonl data/expected.jsonl --shuffle
```

두 부분의 성격이 다르다.

| 부분 | 모델 | 왜 |
|---|---|---|
| 예상 질문 생성 | 필요 | 자연스러운 질문은 규칙으로 못 만든다. 발표 전 작업이라 느려도 된다 |
| 커버리지 판정 | **불필요** | 근거 줄의 수치·핵심어가 답변에 나왔는지 대조하면 끝이다 |

**판정에 모델을 쓰지 않은 게 중요하다.** 여기가 "당신은 이걸 놓쳤다"고 발표자에게
말하는 자리다. 모델이 지어낼 여지가 있으면 안 된다. 환각 방지는 실전 프롬프터만이
아니라 여기서도 지켜져야 한다.

### 유형별로 따로 뽑는다

한꺼번에 시키면 사실확인만 잔뜩 나온다. 손으로 쓴 45개도 47%가 사실확인이었다.
유형마다 호출을 나누니 5/5/5/5 로 고르게 나왔다.

한계반론 질문이 특히 쓸모 있었다. 예:

> 포트홀은 그냥 차가 많이 다니거나 아스팔트가 낡아서 생기는 경우도 많지 않나요?
> 균열이나 이음부 손상은 AI 판독 정확도가 꽤 떨어지던데, 중요한 결함을 놓칠 위험은 없나요?

두 번째는 11번 슬라이드의 AP50 표에서 균열 0.550, 이음부 손상 0.574 가 낮은 것을
읽고 만든 공격이다.

### 커버리지 판정에서 겪은 것

- **퍼센트가 통째로 빠지고 있었다.** 형태소 분석기가 `41` 과 `%` 를 따로 내놓는데
  숫자+단위만 붙이고 기호는 안 붙였다. 이 발표자료는 퍼센트가 도처에 있어서
  그냥 뒀으면 판정이 계속 틀렸다. `41%`, `48.3%` 로 되살린다.
- **흔한 말을 근거로 세면 안 된다.** 처음엔 IDF 상위 6개를 뽑았더니 `대신`, `영상`,
  `실제` 가 "놓친 근거"로 떴다. 발표자에게 "'대신'을 안 말했다"고 알려줘야 소용없다.
  수치를 먼저 넣고 나머지는 흔하지 않은 것만 센다.
- **표 슬라이드는 행이 여럿이다.** 질문으로 고른 줄과 다른 행을 근거로 답해도 틀린 게
  아니다. 같은 슬라이드 안의 수치를 댔으면 따로 표시한다 - 이걸 오답으로 세면
  판정이 거짓말을 한다.

## 꼬리질문 (`drill_graph.py`)

답변이 부족하면 파고든다. 계획서의 '모의 디펜스 꼬리질문 멀티턴 흐름'이다.

```
ask -> (사람 답변 대기) -> judge -> 충분한가?
                                     아니오 -> followup -> ask ...
                                     예     -> 끝
```

### LangGraph 를 여기에만 쓴 이유

계획서는 질문 생성·커버리지 판정·꼬리질문을 다 묶어 LangChain/LangGraph 로 하라고
했지만, 앞의 둘은 상태도 분기도 없는 반복문이라 프레임워크를 넣으면 재시도·캐시 로직만
가려진다. 꼬리질문은 다르다.

1. **사람을 기다리며 멈춘다** -> `interrupt()`
2. **상태가 요청 사이를 넘어간다** -> checkpointer

터미널이면 반복문으로 충분하다. 그런데 실제 제품은 웹앱이라 답변 하나하나가 별개의
요청이다. 지금 어느 질문인지, 꼬리질문 몇 번째인지, 무엇을 아직 못 댔는지를 요청
사이에 들고 있어야 한다.

**저장소는 갈아끼우는 부분이다.** 지금은 `MemorySaver`, 백엔드가 DB 를 정하면
`SqliteSaver` / `PostgresSaver` 로 한 줄 바꾸면 되고 그래프 구조는 안 건드린다.

### 안전장치 둘

**답 유출 차단.** 모델이 만든 꼬리질문에 놓친 수치가 그대로 들어 있으면 버리고
템플릿을 쓴다. "41%가 맞나요?"라고 물으면 연습이 안 된다.

**수치는 끝까지 받아낸다.** 커버리지가 70%를 넘어도 물어본 수치가 안 나왔으면
통과시키지 않는다. "몇 퍼센트였나요"에 주변 사실 셋을 대고 정작 그 수치를 안 말했는데
75%로 통과시키면 실전에서 그대로 막힌다. 다만 꼬리질문은 최대 2회다 - 연습이지
심문이 아니다.

### 꼬리질문 생성은 배치가 아니다 (설계 착오)

"발표 전 작업이라 느려도 된다"고 보고 재시도를 5회로 뒀는데, 실제로는 **발표자가 화면
앞에서 기다리는 중**에 생성된다. 무료 등급 속도 제한에 걸려 질문 하나에 5분씩 멈췄다.

재시도를 1회로 줄여 템플릿으로 빨리 떨어지게 했다(5분 -> 5초). 제대로 된 해법은
`gen` 단계에서 꼬리질문을 미리 만들어두는 것이다 - 그때는 각 질문의 근거를 이미 알고
있으므로 가능하다. 아직 안 했다.

## 연습 -> 실전 환류 (`weak_profile.py`)

세 단계를 각각 만들어놓고 서로 연결을 안 하고 있었다. 모의 디펜스 결과는 화면에
출력하고 끝이었고, 실전 키워드는 연습 기록을 보지 않았다.

```
모의 디펜스 --(무엇을 몇 번 놓쳤나)--> weak.json --(키워드 순서)--> 실전 화면
```

연습에서 자꾸 놓친 근거를 실전 키워드 앞쪽으로 당긴다. 발표자가 제일 까먹는 것이
맨 앞에 와야 한다.

```
연습 전 : ['3,300장', '33,000장', '영상', '대신', '사진', '0.96']
연습 후 : ['33,000장', '3,300장', '영상', '대신', '사진', '0.96']
          (33,000장을 3번 다 놓쳤음 -> 2위에서 1위로)
```

LLM 도 임베딩도 안 쓴다. 세는 것과 정렬이 전부다.

### 계획서보다 짧은 고리다

계획서는 환류를 "다음 발표를 위한 데이터"라고 했다. 그런데 **발표 전날 연습 ->
당일 실전**이라는 더 짧은 고리가 있다. 같은 날 안에서 도니까 효과가 직접적이다.

### 주의

- 순위를 바꾸는 정도로만 민감하게 뒀다(`BOOST = 2.0`). 크게 주면 질문과 무관한
  근거가 올라온다.
- 기록 파일이 깨졌거나 없으면 없는 셈 치고 동작한다. 실전에서 멈추면 안 된다.
- 유형별 약점은 `weak_type` 플래그로 내보낸다. 화면에서 우회 화법을 더 강조할지는
  프론트가 정할 문제다.

## 잡음 방어 · 근거 없음 판정 (QA 요청)

`cue()` 가 검색 전에 두 번 거른다. 둘 다 규칙이고 LLM 을 안 쓴다.

```
질문 --> ① 잡음인가?  --예--> status="ignored"     화면 그대로 둠
          ↓ 아니오
         ② 자료와 관련 있나? --아니오--> status="no_evidence"  근거없음 화면 + 추천 답변
          ↓ 예
         검색 --> status="ok"
```

**두 상태를 나눈 이유가 있다.** 헛기침에 화면이 껌뻑이면 안 되므로 `ignored` 는 화면을
건드리지 않는다. `no_evidence` 는 발표자가 알아야 하므로 화면을 바꾼다.

### 문턱값은 재서 잡았다

감으로 정하면 둘 중 하나가 된다. 낮으면 무관한 질문에도 엉뚱한 근거가 뜨고,
높으면 멀쩡한 질문을 막는다. 관련 질문 45개와 무관한 질문 10개를 같이 넣고 쟀다.

```
관련 질문   낱말 일치율 0.50 ~ 1.00
무관한 질문 낱말 일치율 0.00 ~ 0.50
```

깨끗하게 갈린다. 0.02~0.50 구간이 전부 같은 성능(정상 100% 통과 · 무관 90% 차단)
이라 **구간 한가운데인 0.26** 을 골랐다. 끝값은 표본이 조금만 움직여도 무너진다.

잡음 방어는 10/10 차단하고 정상 질문 오차단은 0건이었다.

### 못 잡는 경우

```
0.50  "이 프로젝트 예산이 얼마나 들었나요?"   <- 통과해버림
```

`예산` 이 발표자료에 실제로 있다(15번 슬라이드 대시보드의 보수 예산). 심사위원이 묻는
개발 예산과는 다른 얘기지만, 낱말이 있는지만 보므로 구별하지 못한다.

이 경우 화면엔 15번 슬라이드가 뜨고 발표자가 보면 아니라는 걸 안다.
**근거가 아예 안 뜨는 것보다는 낫다**고 보고 감수한다.

### 주의

무관한 질문 10개는 내가 지어냈다. 실제 심사에서 나오는 무관한 질문과 다를 수 있으므로,
팀원 질문이 모이면 다시 재야 한다.

## 사후 회고 리포트 (`qa_log.py` · `report.py`)

계획서 [사후] 단계다. 그동안 "실전 로그가 있어야 만든다"고 미뤄왔는데,
**정작 로그를 남기는 코드가 없었다.** 질문이 들어오면 처리하고 버렸다.
그러면 영원히 안 쌓인다. 순환 논리였다.

```bash
python report.py                          # data/qa_log.jsonl 읽기
python report.py -w data/weak.json        # 연습 기록도 같이
```

`cue()` 가 질문마다 한 줄씩 남긴다. 걸러진 것(`ignored`/`no_evidence`)도 남긴다 -
얼마나 자주 걸러지는지가 중요한 지표다. **기록 실패로 발표가 멈추면 안 되므로
예외를 밖으로 내보내지 않는다.**

### 오늘 감으로 정한 것들이 이 파일로 답이 난다

| 미뤄둔 질문 | 리포트가 답하는 것 |
|---|---|
| 요약 기능이 필요한가 | 질문 길이 중앙값 · 60자 넘는 비율 |
| 문턱값이 맞나 | `no_evidence` 비율 (30% 넘으면 경고) |
| 프리셋이 맞나 | 지연 p50/p95 (1초 넘으면 경고) |
| 모의 디펜스가 쓸모 있었나 | 예상 질문 적중률 |

### 적중률의 정의를 고쳤다

처음엔 문장 유사도(자카드)로 쟀더니 **0/6** 이 나왔다. 재보니 같은 주제인 질문쌍도
겹침이 0.06~0.13 밖에 안 됐다. 예상 질문은 길고 문어체인데 실제 질문은 짧고
구어체라 낱말이 겹칠 수가 없다.

```
실제 : "AI 성능이 어느 정도 나왔나요?"
예상 : "CCTV 이미지 데이터는 총 몇 장인가요?"
```

애초에 둘은 다른 질문이다. 문장이 같기를 기대하는 게 잘못이었다.

**발표자에게 의미 있는 건 "우리가 연습한 대목에서 질문이 나왔나"** 다. 그래서 근거
슬라이드가 같은지로 센다. 같은 데이터에서 **6/7(86%)** 이 나왔고, 못 맞힌 하나는
실제로 예상 질문이 다루지 않은 슬라이드였다.

## 키워드 모드 / 추천 답변 모드 (`answer.py`)

QA 에서 키워드만으로는 답변을 만들어 말하기 어렵다는 결과가 나왔다. 회의나 업무 자리는
발표자가 자료를 외우고 있지 않아서 답변 문장이 더 필요하다. 그래서 모드를 고를 수 있게 했다.

| 모드 | 화면 | 모델 호출 |
|---|---|---|
| `keywords` (기본) | 키워드, 근거 슬라이드 | 0회 |
| `answer` | 위와 같고, 1~2초 뒤 추천 답변 2문장이 이어서 뜬다 | 질문당 1회 (gpt-5.4-mini) |

```python
rq = ReadyQ(chunks_path, mode="answer")    # 또는 rq.set_mode("answer")
rq.warm()                                  # answer 모드면 API 연결도 미리 연다

cue = rq.cue(question)
send(cue.to_message())                     # 키워드는 기다리지 않고 먼저 보낸다
if rq.mode == "answer":
    for msg in rq.answer(question, cue):   # 문장이 끝날 때마다 하나씩 나온다
        send(msg)                          # 마지막 msg 는 done=True, status 포함
```

`status` 는 다섯 가지다.

| status | 뜻 | 화면 |
|---|---|---|
| `ok` | 답변 완료 | 답변 표시 |
| `no_answer` | 자료로 답할 수 없음 | 키워드만 |
| `blocked` | 자료에 없는 숫자가 나와서 그 문장부터 버림 | 앞 문장까지만 |
| `error` | 키 없음, 8초 초과 등 | 키워드만 |
| `skipped` | 근거 없음이나 잡음이라 부르지 않음 | 기존 근거 없음 화면 |

### 지어낸 답변을 막는 장치

1. 검색된 슬라이드 3장 내용만 주고 그 안에서만 답하게 한다.
2. 근거 없음이나 잡음으로 판정된 질문은 모델을 부르지 않는다.
3. 문장이 끝날 때마다 숫자를 슬라이드와 대조한다. 화면에 한 번 뜬 숫자는 되돌릴 수 없어서
   답변을 다 받고 검사하지 않고 문장 단위로 검사한다.

### 측정 (톰과젤리, 손으로 쓴 질문 45개, 2026-09-16)

`python eval_answer.py data/chunks_tomjelly.jsonl data/questions_tomjelly.jsonl`

| 항목 | 값 |
|---|---|
| 답변 | ok 43, no_answer 2, blocked 0, error 0 |
| 첫 문장 | 보통 1.4초, 느릴 때(p95) 2.4초 |
| 끝 | 보통 1.7초, 느릴 때(p95) 2.6초 |

처음 측정에서 고친 것 세 가지.

- 클라이언트 timeout 이 스트리밍에서 안 먹어서 60초를 기다렸다. 호출을 작업 스레드로 옮기고 8초에 끊는다.
- 첫 질문만 7.9초 걸렸다. 연결 수립 비용이라 `warm()` 에서 미리 연다.
- "~했습니다" 를 강제했더니 "교통량 요인을 배제하셨나요?" 에 "배제했습니다" 라고 자료보다 세게 답했다.
  단정 금지 규칙을 넣은 뒤 "완전히 배제했다고 말하긴 어렵습니다. 다만 500m 로 넓히면 차이가 사라졌기 때문에..." 로 바뀌었다.

### 미리 만든 모범 답변을 실전에 붙이지 않은 이유

처음엔 모의 디펜스에서 예상 질문과 모범 답변을 미리 만들고, 실전 질문이 연습한 질문과 맞으면
그걸 띄워 호출을 0회로 유지하려 했다. 네 가지 방법으로 맞춰봤는데 전부 틀린 답변을 띄웠다.

| 방법 | 결과 |
|---|---|
| 같은 슬라이드 + 낱말 겹침 | "어떤 API 를 쓰셨나요?" 에 "실패한 건 제외 기준" 답변 |
| 핵심 숫자 포함 확인 | 14개 띄워서 6개 정도만 맞음 |
| 임베딩 유사도 (e5-small, BGE-M3) | 틀린 짝이 맞는 짝보다 점수가 높음. BGE-M3 는 질문당 0.5초 추가 |
| 리랭커 (bge-reranker-base) | 한국어를 못 읽고 질문당 2.6초 |

예상 질문 20개로는 실전 질문을 덮지 못한다. 맞는 짝이 없는 질문에 가장 비슷한 것을 고르면 틀린 답변이 된다.
같은 질문들을 실시간 생성으로 돌리면 "국토교통부 VWorld API 를 사용했습니다" 처럼 맞게 답했다.

모범 답변은 연습 화면에서 쓴다. `mock_defense.py gen` 이 질문과 함께 만들고(호출 1회 추가),
`drill` 에서 발표자가 답한 뒤에 보여준다. 먼저 보여주면 읽고 따라 하는 연습이 된다.
슬라이드에 없는 숫자가 들어간 모범 답변은 버린다(20개 중 2~3개).

생성 모델 비교 (예상 질문 20개):

| 모델 | 결과 |
|---|---|
| gpt-4o | 질문 번호를 "슬라이드2" 로 붙여 한계반론 질문이 통째로 빠짐. 답변 9/15, 동어반복 많음 |
| gpt-5.4-mini | 답변 16/20, 57초. 채택 |
| gpt-5.5 | 답변 13/20, 2분 7초. "없음" 이 많음 |

## 공백이 빠진 PDF와 근거 줄 고르기 (2026-09-17)

로컬 연동 테스트에서 PowerPoint 로 저장한 PDF 의 근거가 "구독500 명으로운영BEP," 처럼 떴다.
문제가 세 겹이었다.

### 1. 띄어쓰기가 통째로 빠짐 (`ingest.py`)

글자 위치를 재봐도 단어 사이 간격이 0 이라 위치로는 복원할 수 없었다.

- 한글 사이 공백 비율로 이런 자료만 골라낸다. 공백 빠진 PDF 0.0, 톰과젤리 0.25, 문턱 0.05
- 형태소 분석기(kiwipiepy)로 띄어쓰기를 다시 넣는다
- 분석기가 모르는 이름과 외래어를 쪼갰다("민 서정", "미들 웨어"). PDF 안 글자 묶음 경계를
  읽어서, 경계가 아닌 자리의 공백은 버린다. "민서정", "미들웨어", "해커톤", "온보딩" 으로 돌아왔다
- 숫자와 단위를 다시 붙인다("10 곳" → "10곳")

### 2. 줄바꿈으로 문장이 끊김 (`ingest.py`)

줄이 쉼표, 조사, 연결 어미로 끝나면 다음 줄과 잇는다. 다음 줄이 글머리표로 시작하거나
너무 짧으면(소제목일 가능성) 안 잇는다. 톰과젤리에서 틀리게 이은 곳은 표지 한 곳이다.

### 3. 근거 줄을 잘못 고름 (`pipeline.py`)

정답 줄을 적은 질문 18개(PotentiAI 자료)로 나눠 보니 슬라이드 검색은 17/18 이 3위 안에 들었고,
틀린 건 줄 고르기였다. 고친 것:

| 원인 | 고친 방법 |
|---|---|
| 표나 카드에서 값이 제목 아래 줄에 따로 있음 ("월 고정비" / "30만원") | 짧은 제목 줄과 바로 아래 짧은 숫자 줄을 합친 후보를 추가 |
| 질문과 자료의 단어가 다르게 끊김 ("구독자"와 "구독", "일치"와 "일치율") | 한쪽이 다른 쪽을 품으면 0.7 배로 인정 |
| 분석기가 이름을 잘못 자름 ("이예진" → "이예지") | 자료에 없는 질문 단어는 원래 어절 글자로 찾음 |
| 숫자만 있으면 가산점 ("특허가출원 참여(10-2026-...)" 가 "경진대회 참여" 를 이김) | 질문 단어가 하나라도 맞은 줄에만, 단위가 붙은 수치에만 가산점 |
| 검색 1위 슬라이드 안에서만 줄을 고름 | 3개 슬라이드의 줄 점수에 검색 순위 가산점(3, 1.5, 0)을 더해 다시 정렬 |

| 측정 | 전 | 후 |
|---|---|---|
| PotentiAI 18문항, 1순위 근거에 정답 줄 | 5 | 9 |
| PotentiAI 18문항, 3개 안에 정답 줄 | 7 | 11 |
| 톰과젤리 45문항, 1순위 슬라이드 정답 | 27 | 30 |

톰과젤리에서 1순위 줄이 바뀐 16문항 중 6개 정도는 좋아지고 3~4개는 나빠졌다.
나빠진 예: "이 분석의 한계는?" 이 "스크리닝 도구이다" 대신 "첫째, 하수관은..." 을 띄운다.
문항 수가 적어 가중치를 더 잘게 맞추지 않았다.

### 준비 직후 첫 질문이 느림

준비 직후 첫 질문 몇 개가 200~280ms, 이후 50~70ms 였다. `warm()` 끝에 길이가 다른 가짜 질문
5개를 흘려서 발표 전에 치르게 했다. 준비 직후 첫 질문이 20~25ms 로 나온다.

로컬 테스트에서 본 0.6~1.2초는 다른 자료의 준비(임베딩 색인)가 동시에 돌던 때였다.
준비 작업은 한 번에 하나만 돌리는 게 맞다(백엔드 `engine_store.py`).

### 어느 발표에나 나오는 질문이 근거 없음으로 막힘 (2026-09-17)

"이 프로젝트를 왜 만드셨죠", "이 프로젝트의 한계", "장점" 이 전부 근거 없음으로 떴다.
근거 없음 판정은 질문 명사가 자료에 있는 비율로 보는데, 19장 자료에 프로젝트, 이유, 한계, 장점이
한 번도 안 나와서 비율이 0 이었다. 발표장에서 제일 흔한 질문을 막은 것이다.

- 이런 말(`META_EXPAND`)은 비율 계산에서 뺀다
- 질문이 이런 말로만 되어 있으면 자료 쪽 표현으로 바꿔 찾는다
  (이유, 왜 → 문제/배경/목적, 한계 → 다만/향후/과제, 장점 → 기존/대비/차별, 뭔가요 → 개요/소개/해결)
- 바꾼 말도 자료에 없으면 그대로 근거 없음

판정 기준 측정(`calibrate_guard.py`)은 고치기 전과 같다. 관련 질문 100% 통과, 무관한 질문 90% 차단.

## 열린 이슈

- 다른 제공사(Anthropic/OpenAI)와의 캡션 품질 비교 미실시. `--provider` 로 갈아끼울 수
  있게 해뒀으니, 위 7개 숫자 기준으로 재면 됩니다.
- `PROVIDERS` 의 openai 기본값(`gpt-4o`)은 미검증입니다. gemini 처럼 낡았을 수 있습니다.

## 통합 지식 조각 (2026-09-19, 로컬 시연용)

검색과 답변 근거가 슬라이드 한 장 단위라 슬라이드 밖 지식이 약했다. 대본, 설명 자료, 리허설 설명이 어느 슬라이드에 억지로 붙거나 "전체" 로 밀렸고, 문장 하나씩 저장해서 "두 방식을 합쳐야 88.9%" 처럼 앞 문장이 없으면 뜻이 끊겼다.

`knowledge.py` 가 출처와 상관없이 지식 조각을 만든다.

| 출처 | 조각 단위 |
|---|---|
| 슬라이드 | AI 정리본(`slide_refine.py`)의 묶음 하나. 정리본이 없으면 원문 6줄씩 |
| 대본, 설명 자료 | 원래 글의 한 문단을 소제목과 함께 (`notes.classify` 가 문장마다 문단 번호와 소제목을 붙인다) |
| 리허설 | 이어진 문장 2개씩 |

추천 답변과 흐름도의 근거는 이 조각을 BM25 + e5-small 로 찾는다. 화면의 키워드와 근거 카드는 지금처럼 슬라이드 검색을 쓴다.

측정 (Ready-Q 발표자료 13장 + 설명 자료, 질문 15개 두 번씩, 정답 낱말이 들어갔는지):

| | 슬라이드 기반 | 지식 조각 |
|---|---|---|
| 설명 자료에만 답이 있는 질문 10개, 답변에 정답 | 12/20 | 20/20 |
| 슬라이드에 답이 있는 질문 5개, 답변에 정답 | 10/10 | 10/10 |
| 평균 응답 | 1.38초 | 1.30초 |

거쳐 온 것:
- 이어진 문장 3개씩 묶었을 때는 12/20 → 17/20 에 그쳤다. 조각이 소제목 경계를 넘어 두 주제가 섞였고, 주제어가 소제목에만 있는 문장("46%에서 55%로") 을 못 찾았다(59위). 문단과 소제목 단위로 바꿨다.
- 슬라이드 반복(repeat)으로 분류된 문장을 빼면 분류가 틀린 설명("20자 미만이면 이미지로 읽는다") 이 통째로 사라졌다. repeat 도 넣는다.

주의: 질문 15개는 설명 자료를 보고 직접 썼다. 표본이 작고, 채점은 정답 낱말 포함 여부다.

## 지식 지도 (2026-09-19, 로컬 시연용)

이름: 조각 사이의 관계는 **지식 지도**(`knowledge_graph.py`, `data/kgraph`), 슬라이드 사이의 관계는 **슬라이드 지도**(`deck_graph.py`, `data/graph`). 화면 탭 이름도 같다.

`knowledge_graph.py` 가 지식 조각마다 짧은 이름과 주제 묶음을 붙이고, 조각 사이를 근거, 원인, 결과, 방법, 예시, 한계, 같은내용으로 잇는다. 준비 단계에서 한 번 만든다(조각 60개 기준 12초, 관계 52개). 조각 번호는 내용에서 만들어 설명을 더해도 나머지 번호가 그대로다.

검색이 찾은 조각의 이웃을 답변 근거에 더하는 것은 **지금은 끈다** (`ReadyQ.use_kg = False`).

| 질문 묶음 | 지표 | 조각만 | 조각 + 그래프 |
|---|---|---|---|
| 여러 조각을 엮어야 하는 질문 8개 x 2회 | 근거에 든 사실 | 88% | 88% |
| | 답변에 든 사실 | 69% | 71% |
| 설명 자료 질문 3개 x 2회 | 답변에 든 사실 | 100% | 83% |

조각 60개 중 8개를 검색하면 이미 필요한 사실의 88% 가 근거에 들어왔다. 그래프로 더할 게 거의 없었다. 근거에는 있는데 답변에서 빠지는 것(88% -> 70%)이 더 컸다. 추천 답변을 2문장으로 제한해서 여러 사실을 다 못 담는다.

근거에서 빠진 한 질문은 "환각을 막기 위해 어떤 장치를 두었나요?" 였다. 자료는 같은 내용을 "지어낸 내용을 막는 방법" 이라고 써서 낱말이 겹치지 않는다. 그래프로도 풀리지 않았다.

이 그래프는 화면의 지식 지도 탭에 쓴다. 자료가 커져서 검색 8개가 전체의 작은 부분이 되면 다시 잰다.

## 슬라이드 지도를 답변 경로에서 뺐다 (2026-09-20)

`deck_graph.py` 의 발표 줄거리를 답변 프롬프트에 넣던 것을 뺐다. 지식 지도 이웃 확장(`use_kg`)은 9월 19일에 이미 꺼둔 상태였다.

Ready-Q 발표자료 초안(13장)과 Ready-Q 설명자료(md, 설명 87개)로 쟀다. 질문 12개(슬라이드로 답하는 것 8개, 설명 자료에만 답이 있는 것 4개)에 답변을 받고, 미리 적어둔 "답변에 나왔어야 할 사실"이 들어갔는지 셌다. 조건마다 2회.

| 조건 | 슬라이드 질문 사실 | 설명자료 질문 사실 |
|---|---|---|
| 슬라이드만 + 지도 | 36/48 (75%) | 0/22 (0%) |
| 슬라이드만, 지도 없음 | 35/48 (73%) | 0/22 (0%) |
| 슬라이드 + 설명 자료 + 지도 | 39/48 (81%) | 14/22 (64%) |
| 슬라이드 + 설명 자료, 지도 없음 | 35/48 (73%) | 12/22 (55%) |

같은 조건의 회차 사이가 3개까지 흔들렸다(18 다음 21, 19 다음 16). 지도 있음과 없음의 차이 2~4개는 그 안이다.

더 분명한 건 구조다. **두 회차 모두 지도가 있으나 없으나 근거로 뽑힌 슬라이드가 12문항 전부 같았다.** 답변 근거는 통합 지식 조각 검색이 고르고, 지도는 프롬프트에 발표 줄거리 한 덩어리를 덧붙일 뿐이라 바뀔 자리가 없었다.

9월 초 측정(설명자료 6장)에서는 지도가 근거 포함 비율을 46% -> 55% 로 올렸다. 그때는 답변이 `_with_graph` 로 이웃 슬라이드를 끌어왔다. 통합 지식 조각 검색으로 바꾸면서 그 역할이 검색으로 넘어갔다. 지도가 틀린 게 아니라 검색이 흡수했다.

답을 실제로 바꾼 것은 설명 자료였다. 설명 자료에만 있는 질문(검색 정확도 88.9%, e5-small 을 고른 이유, 문턱값 0.26)은 슬라이드만으로 0% 였고 설명 자료를 넣으면 55~64% 가 됐다.

바꾼 것
- `_kb_context` 와 `_fallback` 에서 발표 줄거리를 뺐다. 보강 자료가 없으면 `_fallback` 은 None 이고 추론 답으로 넘어간다(전과 같다).
- 준비(warm) 단계에서 지도 두 개를 만들지 않는다. 지도 화면을 열 때 만든다(지식 지도 13.7초, 슬라이드 지도 3.9초, 두 번째부터 0.3초).
- 준비 시간은 같은 발표자료에서 73.3초 -> 56.7초.
- 지도 화면에는 설명이 없는 슬라이드 목록을 넣었다. 측정으로 확인된 지렛대(설명 자료 넣기)로 보내는 자리다.

측정 중 한 번은 모델 호출이 멈춰 절반이 실패했다(한 건은 73분). 그래서 재시도를 넣고 세 번 돌려 성공한 2회로 집계했다. 실전 경로에는 8초 마감이 있어 답변이 늦으면 끊고 근거만 남는다.

## 근거 없음 판정에 의미 유사도를 더해봤다 (2026-09-19) - 바꾸지 않음

근거 없음 판정은 질문 명사가 자료에 있는지만 본다. 뜻이 다른 같은 낱말("보수" 급여와 수리)을 구별하지 못한다. e5-small 임베딩으로 질문과 가장 가까운 지식 조각의 유사도(query:, passage: 머리말)를 더해봤다.

톰과젤리 18장, 기존 질문 55개에 동음이의어 질문 8개("보수는 얼마나 받으셨어요?", "지도 교수님은 누구세요?")와 다른 표현 질문 8개("땅꺼짐이 제일 많이 생기는 이유가 뭔가요?")를 더했다.

| 질문 묶음 | 의미 유사도 (중앙값) |
|---|---|
| 관련 45 | 0.806 ~ 0.892 (0.851) |
| 다른 표현 8 | 0.793 ~ 0.856 (0.838) |
| 무관 10 | 0.794 ~ 0.834 (0.820) |
| 동음이의어 8 | 0.787 ~ 0.837 (0.834) |

| 규칙 | 관련 통과 | 다른 표현 통과 | 무관 차단 | 동음이의어 차단 |
|---|---|---|---|---|
| 지금 (낱말 0.26) | 45/45 | 7/8 | 9/10 | 1/8 |
| 의미만 0.84 | 33/45 | 3/8 | 10/10 | 8/8 |
| 낱말 그리고 의미 0.82 | 44/45 | 5/8 | 9/10 | 4/8 |
| 낱말 또는 의미 0.83 | 45/45 | 8/8 | 8/10 | 0/8 |

동음이의어 점수가 관련 질문과 겹친다. 막으려면 관련 질문도 같이 막힌다. e5-small 은 같은 분야인지는 잡지만 뜻이 갈리는 낱말을 구별할 만큼 점수가 벌어지지 않는다. 지금 규칙을 그대로 둔다. 뜻 구별은 추천 답변과 흐름도를 만드는 모델이 한다(자료로 답할 수 없으면 추론 답으로 표시). 질문 16개는 직접 썼고 표본이 작다.

## 숫자 검사가 모델 이름 속 숫자를 막던 문제 (2026-09-21)

추천 답변과 흐름도는 문장마다 숫자를 자료와 대조한다(`answer.numbers_ok`). 이 검사가 `\d+` 로 숫자를 뽑아서
`BM25` 의 25, `e5-small` 의 5 도 수치로 취급했다. "검색 방식은 왜 BM25와 e5-small을 합쳤나요?" 에 답변이
"BM25와 e5-small을 함께 쓴 것은..." 이라고 질문의 이름을 되받았는데, 자료에 `BM25` 가 없다는 이유로
`blocked` 가 되어 답이 통째로 사라졌다(자료에 이유가 없는 질문은 추론 답으로 나오므로 특히 자주 걸린다).

고친 것: 글자에 붙은 숫자(`BM25`, `e5-small`, `gpt-5.4-mini`, `GPT-4o`)는 이름 하나로 보고,
**그 이름이 자료에 있거나 질문에 나왔으면** 통과시킨다. 이름은 대소문자, 띄어쓰기, 하이픈이 달라도 같은 이름으로 본다.

바꾸지 않은 것:
- 질문에서 허용하는 것은 이름뿐이다. "정확도가 95% 인가요?" 에 "네, 95% 입니다" 는 여전히 막는다.
- 자료에도 질문에도 없는 이름은 예전처럼 숫자를 자료와 대조한다.
- `mock_defense.answer_ok`, `core_answers`, `deck_graph` 의 같은 검사는 그대로다(질문이 없는 자리라서 손대지 않았다).

`python eval_numbers.py` 가 이전 판정과 지금 판정을 나란히 보여준다(13개 중 13개 일치, 이전에 막던 5개가 통과).

**알려진 한계.** 숫자 단위로 대조하므로 이름의 다른 버전은 못 잡는다. 자료에 `e5-small` 이 있는데 답변이
`e5-large` 라고 하면 숫자 5 가 자료에 있어서 통과한다. 이전 판정도 같았다. 이름이 자료에 없으면 무조건 막는 식으로
조이면 멀쩡한 답이 더 자주 막힐 것 같아 하지 않았다. 측정 없이 조인 값이라 나중에 실제 질문 기록으로 다시 봐야 한다.
