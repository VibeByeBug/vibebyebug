# Ready-Q — AI 모듈

담당: 이예진 · 팀 레포 `VibeByeBug/vibebyebug`

## 백엔드와의 계약 (STT 무관)

AI 모듈은 STT 구현을 모릅니다. 아래 두 메시지만 들어오면 동작합니다.

```
C→S  {type:"stt.partial", text, ts}    # 말하는 중 (투기적 검색 시작)
C→S  {type:"stt.final",   text, ts}    # 발화 종료
S→C  {type:"cue.evidence", keywords[], sources:[{slide, snippet}], latency_ms}
S→C  {type:"cue.summary",  summary, question_type, delta:true}
```

STT 선정 필수 조건: **interim(부분) 결과 스트리밍 지원.** 없으면 투기적 파이프라인이
불가능해 1초 예산이 깨집니다. 그리고 "발화 끝 → final 도착" 지연을 측정해서 알려주세요 —
그 값이 AI 쪽 예산의 입력값입니다.

## 인덱싱 파이프라인 (두 경로)

발표자료는 두 종류입니다. 둘 다 `chunks.jsonl` 이라는 같은 형식으로 끝나므로,
그 뒤(임베딩·검색)는 어느 경로로 왔는지 구분할 필요가 없습니다.

```
글자가 살아있는 자료 ─ ingest.py ─────────────┐
                                              ├─→ chunks.jsonl → 임베딩 → 검색
글자가 이미지인 자료 ─ render.py → caption.py ─┘
```

`ingest.py` 는 텍스트를 못 찾으면 **조용히 0건을 쓰지 않고 종료코드 3으로 실패**합니다.
검색이 못 보는 구간을 발표자가 모르는 것이 이 제품에서 가장 위험한 실패 양상이라,
파이프라인 전체가 "못 읽었으면 반드시 말한다"를 지킵니다.

## 스크립트

| 파일 | 역할 | 상태 |
|---|---|---|
| `ingest.py` | PDF/PPTX → 슬라이드 단위 청크 | 동작 확인 |
| `quality_report.py` | 추출 품질 게이트 | 동작 확인 |
| `render.py` | 슬라이드 → PNG (PowerPoint COM / PyMuPDF) | 동작 확인 |
| `caption.py` | PNG → 검색용 텍스트 (멀티모달) | 동작 확인 (gemini) |
| `embedders.py` | BM25 / BGE-M3 / KURE-v1 / Gemini / 하이브리드 | 동작 확인 |
| `eval_retrieval.py` | Recall@k · MRR 비교 | 동작 확인 |
| `make_questions.py` | 평가용 질문 생성 (손으로 쓴 질문셋이 기본) | 동작 확인 |
| `eval_typing.py` | LLM 없는 유형 분류 정확도 | 동작 확인 |
| `qtype.py` | 질문 유형 판정 (정규식, 0ms) | 동작 확인 |
| `diagnose_misses.py` | 틀린 질문에 무엇이 대신 올라왔는지 | 동작 확인 |
| `pipeline.py` | **핫패스 - 백엔드가 붙일 대상** | 동작 확인 |
| `mock_defense.py` | **모의 디펜스** — 예상 질문 생성 + 커버리지 판정 | 동작 확인 |
| `drill_graph.py` | 꼬리질문 멀티턴 (LangGraph) | 동작 확인 |

```bash
# 글자가 있는 자료
python ingest.py 발표자료.pptx -o data/chunks.jsonl
python quality_report.py data/chunks.jsonl        # 0=양호 1=경고 2=실패

# 글자가 이미지인 자료
python render.py 발표자료.pptx -o data/slides
python caption.py data/slides --dry-run           # 호출 건수 미리보기 (키 불필요)
python caption.py data/slides -o data/chunks.jsonl --source 발표자료.pptx
```

API 키는 환경변수로 둡니다 (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`).
`caption.py` 가 설정된 키를 보고 제공사를 자동 선택하며, `--provider` 로 덮어쓸 수 있습니다.
캡션은 슬라이드 이미지 + 프롬프트 + 모델명을 해시해 캐시하므로, 다시 돌려도 중복 호출이 없고
프롬프트나 모델을 바꾸면 자동으로 무효화됩니다.

## 설계 결정

**청크 단위 = 슬라이드.** 산출물이 "키워드 + 슬라이드 출처"라서 인용 단위가 곧 검색
단위입니다. 더 잘게 쪼개면 검색은 나아져도 "몇 번 슬라이드"를 못 돌려줍니다.

**캡션은 요약이 아니라 전사.** 모델이 지어낸 문장이 근거로 저장되면 Ready-Q 가 내세우는
'환각 방지'가 인덱싱 단계에서부터 무너집니다. 프롬프트에서 요약·반올림·추측을 금지하고
"안 보이면 빼라"를 명시합니다.

**핫패스에서 LLM 빼기 (검증 대상).** 유형 태그는 분류 문제라 임베딩+분류기로 ~20ms,
1줄 요약은 STT 텍스트 자체로 갈음 가능. 되면 첫 렌더가 STT 지연에만 묶입니다.

## 무료 등급 속도 제한 주의

Gemini 무료 등급은 **모델당 분당 5회**입니다. 워커를 4개로 두면 바로 429 가 나서
18장 중 6장이 통째로 날아갑니다(실제로 겪음). 그래서:

- 기본 워커 수를 2로 낮췄습니다.
- 429 를 만나면 서버가 알려준 `retryDelay` 만큼 기다렸다 재시도합니다(최대 6회).
- 404 처럼 기다려도 소용없는 오류는 즉시 포기합니다.

모델명이 바뀌는 것도 겪었습니다 — `gemini-2.5-flash` 는 신규 사용자에게 막혀 있어
`gemini-3.6-flash` 로 바꿨습니다. 모델 ID 는 하드코딩하지 말고 `--model` 로 넘기세요.

## [정정] 지연 측정이 틀렸었다 (2026-09-05)

아래 bake-off 표의 `질의ms` 는 **틀린 값이다.** 질문 45개를 한 번에 넣고 45로 나눠 쟀는데,
그러면 모델 호출 한 번을 45개가 나눠 써서 실제보다 싸게 나온다.
실제 서비스는 질문이 하나씩 들어온다.

    묶어서 45개 : 질문당 378ms   <- 이렇게 쟀다
    하나씩      : 질문당 595ms   <- 실제

정확도(R@1/R@3/R@5/MRR)는 영향 없다. 지연만 틀렸다.
`eval_retrieval.py` 는 이제 질문 하나씩 재고 p50 과 **p95** 를 같이 낸다.

### 다시 잰 값 (문서 289장, 질문 45개, 질문 하나씩)

| 검색기 | R@3 | p50 | p95 | 색인(warm) |
|---|---|---|---|---|
| hybrid(BM25+BGE-M3) | 93.3% | 584ms | **2,215ms** | 721초 |
| **hybrid(BM25+e5-small)** | **88.9%** | **169ms** | **428ms** | **62초** |
| BGE-M3 단독 | 84.4% | 421ms | 608ms | 515초 |
| BM25 단독 | 80.0% | 0.7ms | 1.2ms | 0초 |
| e5-small 단독 | 75.6% | 93ms | 206ms | 122초 |
| ko-sroberta 단독 | 68.9% | 142ms | 384ms | 88초 |

**BGE-M3 하이브리드는 핫패스에서 못 쓴다.** p95 2.2초는 1초 예산의 두 배다.
스무 번에 한 번은 발표자가 이미 답을 시작한 뒤에 근거가 뜬다. 색인도 12분이다.

**권장: `BM25 + e5-small`.** 정확도 4.4%p 를 내주고 p95 를 5분의 1로 줄인다.
e5-small 은 118M 으로 BGE-M3(568M)의 5분의 1이다. 실시간에 인코딩하는 것은
질문 한 줄뿐이므로 큰 모델이 과하다.

**임베딩 단독으로는 못 쓴다.** e5-small 혼자면 75.6% 로 BM25(80.0%)보다도 낮다.
BM25 와 묶어야 88.9% 가 된다. 단어 매칭과 의미 매칭을 합쳐야 한다는 결론은 그대로다.

### p50 이 아니라 p95 로 예산을 잡을 것

BGE-M3 하이브리드는 p50 584ms / p95 2,215ms 로 3.8배 벌어진다.
평균이 예산 안이어도 스무 번에 한 번 넘으면 발표 중에는 그게 사고다.

### 최종 선택은 STT 측정값에 달렸다

    STT 400ms -> 남는 600ms -> BGE-M3 하이브리드도 검토 가능
    STT 800ms -> 남는 200ms -> e5-small 도 p95 로는 빠듯

백엔드의 "발화 끝 -> final 도착" 측정값이 오면 확정한다. 세 후보를 다 살려둔다.

## 검색기 bake-off 결과 (2026-09-04)

문서 289장(톰과젤리 18 + 랩미팅 10편 271), 손으로 쓴 질문 45개 기준.

| 검색기 | R@1 | R@3 | R@5 | MRR | 질의당 |
|---|---|---|---|---|---|
| **hybrid(BM25+BGE-M3)** | **71.1%** | **93.3%** | **95.6%** | **0.817** | 216.8ms |
| KURE-v1 | 66.7% | 88.9% | 93.3% | 0.769 | 194.1ms |
| BGE-M3 | 66.7% | 84.4% | 88.9% | 0.762 | 312.9ms |
| BM25 | 57.8% | 80.0% | 82.2% | 0.683 | **0.9ms** |

**문서 수를 늘리자 순위가 뒤집혔다.** 톰과젤리 18장만 썼을 때는 KURE-v1 이 R@3 95.6% 로
1위였는데, 방해 문서 271장을 넣자 88.9% 로 떨어졌다. 같은 조건에서 hybrid 만 93.3% 그대로였다.

| 검색기 | R@3 (18장) | R@3 (289장) | 변화 |
|---|---|---|---|
| hybrid | 93.3% | 93.3% | 0 |
| KURE-v1 | 95.6% | 88.9% | -6.7 |
| BGE-M3 | 91.1% | 84.4% | -6.7 |
| BM25 | 88.9% | 80.0% | -8.9 |

hybrid 는 단어 매칭(BM25)과 의미 매칭(임베딩) 두 신호를 RRF 로 합치므로, 방해 문서가
한쪽을 속여도 다른 쪽이 잡는다. 단일 검색기는 그 하나가 속으면 방법이 없다.

**결론: hybrid 를 쓰되 2단계로 띄운다.**

```
질문 들어옴 -> BM25 결과 즉시 표시  (0.9ms,  R@3 80%)
            -> hybrid 로 갱신       (217ms,  R@3 93%)
```

BM25 혼자서도 열 중 여덟은 맞고 1ms 면 체감 지연이 없다.

**다만 2단계에서 순서가 거의 매번 바뀐다.** 실측 8개 중 7개에서 상위 3개가 달라졌다.
'1단계가 대체로 맞고 2단계가 가끔 고쳐준다'는 전제는 성립하지 않는다.
발표자가 이 흔들림을 견딜 수 있는지는 숫자로 답할 수 없고 화면에 띄워봐야 안다.

**주의: 표본이 작다.** 질문 45개라 hybrid 와 KURE-v1 의 차이(93.3 vs 88.9)는 질문 2개다.
믿을 값은 절대 순위가 아니라 **"방해 문서를 넣었을 때 hybrid 만 안 떨어졌다"는 패턴**이다.
검색기 4개에서 방향이 일관됐다.

**남은 약점: 절차형 질문.** 놓친 3개가 전부 내용이 아니라 '어떻게/왜'를 묻는 질문이었다.
문서 18장일 때도 같은 패턴이라 검색기 교체로 풀릴 문제가 아니다.

## 질문셋을 손으로 쓴 이유

`make_questions.py` 로 모델에게 시켰더니 무료 등급 분당 5회 제한 + 503 혼잡 + DNS 오류로
45분간 한 개도 못 얻었다. 캡션 결과가 이미 로컬에 있어 직접 읽고 쓰는 편이 빠르고,
'슬라이드 문장 베끼지 않기 / 정답 숫자 넣지 않기' 규칙을 확실히 지킬 수 있다.
질문에 숫자가 섞였는지는 자동 점검한다(현재 0건).

정답은 **여러 개를 허용**한다(`gold_ids`). 이 발표는 `6,447곳` 이 6개 슬라이드에 반복 등장해서,
정답을 하나로 고정하면 검색기가 맞는 슬라이드를 찾고도 오답 처리된다.

## 질문 유형 분류 (2026-09-04)

핫패스 산출물이 '요약 1줄 + 유형 태그' 라, 유형 태그를 LLM 없이 뽑을 수 있는지 쟀다.

| 방법 | 정확도 | 비용 |
|---|---|---|
| **키워드 규칙 (`qtype.classify`)** | **93.3%** | **0ms** |
| 최다 클래스만 찍기 | 46.7% | 0ms |
| 임베딩(BGE-M3) + kNN | 42.2% | 모델 2.2GB |

**임베딩이 아무거나 찍는 것보다 못하다.** 한계반론은 6개 중 0개를 맞혔다.
임베딩은 '무슨 얘기인지'를 벡터로 만드는데 유형은 '어떻게 묻는지'로 정해지기 때문이다.
"AI 성능이 얼마나 나왔나요"(사실확인)와 "AI가 틀리면 어떻게 되나요"(한계반론)는
주제가 같아 임베딩상 이웃이지만 유형이 다르다.

**결론: 핫패스에서 LLM 도 임베딩도 뺀다.** 유형 태그는 정규식으로 끝난다.

유형은 '발표자가 어떻게 대응해야 하는가' 로 나눴다. 태그가 떠도 대응이 안 달라지면
쓸모없는 정보다.

| 유형 | 비중 | 발표자가 할 일 |
|---|---|---|
| 사실확인 | 47% | 숫자를 그대로 읽으면 끝 |
| 절차 | 24% | 단계를 순서대로 |
| 근거 | 16% | 검증 슬라이드로 |
| 한계반론 | 13% | 방어·우회 화법 (계획서의 우회 템플릿이 여기서 발동) |

**주의:** 규칙을 45개의 정답을 본 뒤에 썼고, 오답을 보고 한 번 더 고쳤다. 93.3% 는
낙관적이다. 임베딩은 leave-one-out 교차검증을 했고 규칙은 안 했으므로 공정한 비교도
아니다. 다만 "임베딩이 최다 클래스 찍기보다 못하다" 는 규칙과 무관하게 성립한다.

## 절차형 질문 - 시도 두 개 다 실패 (2026-09-04)

hybrid 가 놓친 3개가 전부 '어떻게/왜' 를 묻는 절차형이었다. `diagnose_misses.py` 로
무엇에 밀렸는지 봤더니 원인이 둘이었다.

1. **희석** - 답이 긴 슬라이드의 한 줄에 있는데 슬라이드 전체를 통으로 채점하니,
   처음부터 끝까지 그 주제인 슬라이드가 이긴다.
2. **어휘 격차** - 질문 "순위를 매길 때 뭘 먼저 보고 정하신 건가요" 와
   슬라이드 "선정 규칙 : (1) 사고 유무 -> (2) 보수 횟수" 는 같은 뜻인데 겹치는 글자가 없다.

### 시도 1: 구간 단위 채점 (`MaxPassage`) - 채택 안 함

| 검색기 | R@3 | 질의당 |
|---|---|---|
| hybrid (기존) | 93.3% | 216.8ms |
| hybrid + 구간채점 | 93.3% | **1,302ms** |
| BGE-M3 단독 | 84.4% | 244ms |
| BGE-M3 + 구간채점 | **91.1%** | 604ms |

놓친 질문 3개가 그대로다. 희석은 실재해서 **임베딩 단독은 +6.7%p** 올랐지만,
하이브리드는 BM25 가 이미 그 부분을 보완하고 있어 더 얻을 게 없었다.
그리고 1,302ms 는 1초 예산을 검색 혼자 넘긴다. **임베딩 하나만 쓸 때는 유효한 카드다.**

### 시도 2: 유형별 검색어 확장 (`qtype.EXPANSION`) - 폐기

| 검색기 | R@3 | 변화 |
|---|---|---|
| BM25 | 80.0% -> **68.9%** | -11.1%p |
| hybrid | 93.3% -> **84.4%** | -8.9%p |

확장어("규칙 선정 기준 순서 단계 ...")가 거의 모든 슬라이드에 있는 흔한 말이다.
BM25 는 드문 단어에 높은 점수를 주는데 흔한 단어를 얹으니 질문을 구별해주던 단어가
묻혔다. 표적 3개를 건지려다 나머지 42개를 망가뜨렸다.

### 결론

**기존 hybrid 217ms 를 그대로 쓴다.** 절차형 일부가 4~6위로 밀리는 것은 안고 간다.
다시 볼 곳은 검색이 아니라 제품 쪽이다 - hybrid 의 R@5 가 95.6% 이므로, 화면에 근거를
3개가 아니라 5개 띄우면 검색을 안 건드리고 일부가 회수된다. 프론트와 정할 문제다.

## [결정] 2단계를 버리고 한 번에 띄운다 (2026-09-05)

처음엔 BM25 로 즉시 띄우고(3ms) 정확한 결과로 갱신하는(428ms) 2단계로 설계했다.
"빈 화면이 제일 나쁘다"는 전제였는데, **그 전제를 검증하지 않았다.**

실측해보니 8개 질문 중 **4개에서 1위 카드가 교체**되고 7개에서 순서가 바뀌었다.
그리고 갱신이 428ms 에 도착한다 - **발표자가 화면으로 눈을 옮기는 시간과 비슷하다.**

    질문 종료 -> (발표자가 질문을 소화하고 고개를 돌림) -> 눈이 카드에 닿음
                                                            ^ 이 순간 내용이 바뀐다

1단계를 읽을 틈은 없고 바뀌는 것만 보인다. **값은 못 하고 흔들림만 남는다.**
428ms 빈 화면은 사람이 '느리다'고 느끼는 구간(대략 1초)에 한참 못 미친다.

**그래서 단일 단계로 간다.** API 도 계약도 단순해졌다 - `rq.cue(question)` 하나다.

2단계 비교용 메서드(`_fast_cue` / `_refined_cue`)는 진단용으로 남겨둔다.

## 핫패스 (`pipeline.py`)

백엔드가 붙일 대상이다. STT 구현을 모르고 텍스트만 받는다.

```python
rq = ReadyQ("data/chunks.jsonl")   # 기본 = balanced
rq.warm()                           # 발표 시작 전 1회

cue = rq.cue(question)              # 이거 하나면 된다
cue.to_message()                    # cue.evidence 형태의 dict
```

**중간 결과를 먼저 띄우지 않는다.** 기다렸다 한 번에 준다.

2단계 검색기는 프리셋으로 고른다. 어느 걸 쓸지는 STT 가 예산을 얼마나 쓰느냐로 정해진다.

| 프리셋 | 구성 | R@3 | p50 | p95 | 색인 |
|---|---|---|---|---|---|
| `fast` | BM25 만 (2단계 없음) | 80.0% | 0.7ms | 1.2ms | 0초 |
| **`balanced`** (기본) | BM25 + e5-small | 88.9% | 169ms | 428ms | 62초 |
| `accurate` | BM25 + BGE-M3 | 93.3% | 584ms | 2,215ms | 721초 |

```python
rq = ReadyQ("data/chunks.jsonl", preset="fast")      # 2단계 없음
```
```bash
python pipeline.py data/chunks.jsonl "질문" --preset fast
```

`fast` 는 `warm()` 이 0초에 끝나고, `refined_cue()` 를 부르면 **조용히 넘어가지 않고**
왜 안 되는지 말한다. 조용한 실패 경로를 만들지 않는다.

```bash
python pipeline.py data/chunks_tomjelly.jsonl "이 분석의 한계는 뭐라고 보시나요?"
```

내보내는 메시지 (`Cue.to_message()`):

```json
{
  "type": "cue.evidence",
  "question_type": "한계반론",
  "keywords": ["개별", "예측", "도구", "스크리닝", "우선순위"],
  "sources": [
    {"slide": 17, "snippet": "• 개별 사고를 예측하는 도구가 아니라, ...", "source": "발표.pptx"}
  ],
  "deflect": ["그 부분은 저희도 한계로 보고 있습니다. 자료에 이렇게 적어뒀습니다 —"],
  "stage": "fast",
  "latency_ms": 1.2
}
```

`deflect` 는 한계반론 유형에만 붙는다. 계획서의 우회 화법이 여기서 나온다.
답을 대신 만들지 않고 '말하는 방식'만 제안한다.

### 키워드는 만들지 않고 뽑는다

계획서의 '환각 방지' 가 지켜지는 지점이다. 슬라이드에 실제로 있는 줄을 고르고,
그 줄에서 명사만 꺼낼 뿐이다. 없는 말은 화면에 뜨지 않는다.

**형태소 분석기(kiwipiepy)를 쓴다.** 정규식으로 조사를 자르는 방식은 '많았기',
'찾도록', '둘째' 같은 동사·부사 조각을 못 걸렀다. 화면에 뜨는 키워드라 바로 티가 난다.
숫자는 뒤따르는 단위와 다시 붙인다(`3` + `회` -> `3회`). Q&A 는 수치를 물어보므로
`1.47배`, `33,000장`, `0.96` 같은 형태가 살아 있어야 한다.

**줄별 명사는 색인 때 미리 계산한다.** 질의마다 후보 슬라이드의 모든 줄을 분석하면
74ms 가 붙었다. 미리 해두니 1.2ms 다(60배).

### 유형 태그가 여기서 값을 한다

검색에 유형을 쓰는 건 실패했지만(위 참고), **무엇을 띄울지** 고르는 데는 맞다.

| 유형 | 어떤 줄을 밀어주나 |
|---|---|
| 사실확인 | 숫자가 있는 줄 |
| 절차 | (1)(2)(3), 규칙, 순서, 단계가 있는 줄 |
| 근거 | p=, ρ, 배, %, 검증, 대조가 있는 줄 |
| 한계반론 | 한계, 아니라, 제외, 가상, 근사가 있는 줄 + 우회 화법 |

## 모의 디펜스 (`mock_defense.py`)

계획서의 [사전] 단계다. 발표 전에 예상 질문으로 연습하고 무엇을 놓쳤는지 본다.

```bash
python mock_defense.py gen   data/chunks.jsonl -o data/expected.jsonl --per-type 5
python mock_defense.py drill data/chunks.jsonl data/expected.jsonl --shuffle
```

두 부분의 성격이 다르다.

| 부분 | 모델 | 왜 |
|---|---|---|
| 예상 질문 생성 | 필요 | 자연스러운 질문은 규칙으로 못 만든다. 발표 전 작업이라 느려도 된다 |
| 커버리지 판정 | **불필요** | 근거 줄의 수치·핵심어가 답변에 나왔는지 대조하면 끝이다 |

**판정에 모델을 쓰지 않은 게 중요하다.** 여기가 "당신은 이걸 놓쳤다"고 발표자에게
말하는 자리다. 모델이 지어낼 여지가 있으면 안 된다. 환각 방지는 실전 프롬프터만이
아니라 여기서도 지켜져야 한다.

### 유형별로 따로 뽑는다

한꺼번에 시키면 사실확인만 잔뜩 나온다. 손으로 쓴 45개도 47%가 사실확인이었다.
유형마다 호출을 나누니 5/5/5/5 로 고르게 나왔다.

한계반론 질문이 특히 쓸모 있었다. 예:

> 포트홀은 그냥 차가 많이 다니거나 아스팔트가 낡아서 생기는 경우도 많지 않나요?
> 균열이나 이음부 손상은 AI 판독 정확도가 꽤 떨어지던데, 중요한 결함을 놓칠 위험은 없나요?

두 번째는 11번 슬라이드의 AP50 표에서 균열 0.550, 이음부 손상 0.574 가 낮은 것을
읽고 만든 공격이다.

### 커버리지 판정에서 겪은 것

- **퍼센트가 통째로 빠지고 있었다.** 형태소 분석기가 `41` 과 `%` 를 따로 내놓는데
  숫자+단위만 붙이고 기호는 안 붙였다. 이 발표자료는 퍼센트가 도처에 있어서
  그냥 뒀으면 판정이 계속 틀렸다. `41%`, `48.3%` 로 되살린다.
- **흔한 말을 근거로 세면 안 된다.** 처음엔 IDF 상위 6개를 뽑았더니 `대신`, `영상`,
  `실제` 가 "놓친 근거"로 떴다. 발표자에게 "'대신'을 안 말했다"고 알려줘야 소용없다.
  수치를 먼저 넣고 나머지는 흔하지 않은 것만 센다.
- **표 슬라이드는 행이 여럿이다.** 질문으로 고른 줄과 다른 행을 근거로 답해도 틀린 게
  아니다. 같은 슬라이드 안의 수치를 댔으면 따로 표시한다 - 이걸 오답으로 세면
  판정이 거짓말을 한다.

## 꼬리질문 (`drill_graph.py`)

답변이 부족하면 파고든다. 계획서의 '모의 디펜스 꼬리질문 멀티턴 흐름'이다.

```
ask -> (사람 답변 대기) -> judge -> 충분한가?
                                     아니오 -> followup -> ask ...
                                     예     -> 끝
```

### LangGraph 를 여기에만 쓴 이유

계획서는 질문 생성·커버리지 판정·꼬리질문을 다 묶어 LangChain/LangGraph 로 하라고
했지만, 앞의 둘은 상태도 분기도 없는 반복문이라 프레임워크를 넣으면 재시도·캐시 로직만
가려진다. 꼬리질문은 다르다.

1. **사람을 기다리며 멈춘다** -> `interrupt()`
2. **상태가 요청 사이를 넘어간다** -> checkpointer

터미널이면 반복문으로 충분하다. 그런데 실제 제품은 웹앱이라 답변 하나하나가 별개의
요청이다. 지금 어느 질문인지, 꼬리질문 몇 번째인지, 무엇을 아직 못 댔는지를 요청
사이에 들고 있어야 한다.

**저장소는 갈아끼우는 부분이다.** 지금은 `MemorySaver`, 백엔드가 DB 를 정하면
`SqliteSaver` / `PostgresSaver` 로 한 줄 바꾸면 되고 그래프 구조는 안 건드린다.

### 안전장치 둘

**답 유출 차단.** 모델이 만든 꼬리질문에 놓친 수치가 그대로 들어 있으면 버리고
템플릿을 쓴다. "41%가 맞나요?"라고 물으면 연습이 안 된다.

**수치는 끝까지 받아낸다.** 커버리지가 70%를 넘어도 물어본 수치가 안 나왔으면
통과시키지 않는다. "몇 퍼센트였나요"에 주변 사실 셋을 대고 정작 그 수치를 안 말했는데
75%로 통과시키면 실전에서 그대로 막힌다. 다만 꼬리질문은 최대 2회다 - 연습이지
심문이 아니다.

### 꼬리질문 생성은 배치가 아니다 (설계 착오)

"발표 전 작업이라 느려도 된다"고 보고 재시도를 5회로 뒀는데, 실제로는 **발표자가 화면
앞에서 기다리는 중**에 생성된다. 무료 등급 속도 제한에 걸려 질문 하나에 5분씩 멈췄다.

재시도를 1회로 줄여 템플릿으로 빨리 떨어지게 했다(5분 -> 5초). 제대로 된 해법은
`gen` 단계에서 꼬리질문을 미리 만들어두는 것이다 - 그때는 각 질문의 근거를 이미 알고
있으므로 가능하다. 아직 안 했다.
